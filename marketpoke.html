프로젝트 소개

주제

POS·상권·기상·유동인구·행사 데이터를 결합해 매장의 매출 변화 원인을 분석하고, AI가 대응 전략을 추천합니다. 추천된 전략은 담당자 승인을 거쳐 실행되며, 실행 이후 실제 매출과 고객 반응까지 검증하는 흐름으로 설계했습니다.

전체 아키텍처

ECS Fargate 위에 Spring Boot API, FastAPI, Celery Worker, Celery Beat를 각각 올리고, RDS(MySQL)와 ElastiCache for Redis를 Private data subnet에 배치했습니다. 매출 CSV, AI 모델, RAG 인덱스와 분석 로그는 S3에 저장하고, 외부 API(공공데이터·카카오맵·OpenAI)는 NAT gateway를 통해 호출합니다.

DB 설계 및 운영

프로젝트 전체 기능을 도메인별로 설계하고, Spring Data JPA와 MySQL 8로 데이터 정합성을 관리했습니다. 주문·상품 간 관계와 판매 시점 가격 보존 구조를 적용했으며, Redis와 Docker Compose로 세션·작업 상태 및 DB 운영 환경을 구성했습니다.

Spring Boot 관리자 기능으로 JWT 기반 인증·인가, 공지사항 CRUD, S3 첨부파일 업로드·다운로드를 구현했습니다.

Troubleshooting

트러블 슈팅

Trouble 01

장시간 매출 분석으로 인한 API 응답 지연

문제

사용자가 매출 분석을 요청하면 FastAPI가 CSV 처리, 데이터 병합, 통계 분석, AI 추론을 모두 완료한 후 결과를 반환하는 동기 처리 구조였습니다. 분석 시간이 길어질수록 HTTP 요청이 오래 유지되었고, 요청이 몰리면 일반 API 요청까지 지연되었습니다.

진단

장시간 수행되는 분석 작업이 HTTP 요청 내부에서 실행되고, 분석 작업과 일반 API 요청이 동일한 실행 환경을 공유하고 있었습니다. CPU 사용량이 높은 데이터 처리와 AI 추론이 요청 처리 자원을 점유해, 분석 시간에 비례해 API 응답 시간이 증가하는 구조였습니다.

해결
기존 · Client → FastAPI → 매출 분석 → 결과 반환
개선 · Client → FastAPI → Redis Queue → Celery Worker → 매출 분석
01
구조 개선 - FastAPI는 분석 요청을 Redis Queue에 등록한 뒤 Job ID를 즉시 반환
02
Worker 분리 - CSV 처리·데이터 병합·통계 계산·AI 추론은 Celery Worker가 담당하고, 요청 증가 시 API 서버와 별개로 Worker 수 조절
03
상태·실패 관리 - Job API로 진행 상태와 결과를 조회하고, 60초 주기로 queued 20분·running 15분 초과 작업을 FAILED 처리

배운 점

장시간 수행되는 AI·데이터 분석 작업은 일반 HTTP 요청과 분리해야 합니다. 비동기 시스템은 작업을 Queue에 전달하는 것만으로 완성되지 않고, 작업 상태 관리·실패 처리·정체 작업 정리까지 함께 설계해야 안정적으로 운영할 수 있다는 점을 배웠습니다.
