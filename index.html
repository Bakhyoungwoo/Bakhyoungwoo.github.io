Troubleshooting장시간 매출 분석으로 인한 API 응답 지연
문제
FastAPI가 CSV 처리·데이터 병합·통계 분석·AI 추론을 모두 끝낸 뒤 응답하는 동기 구조. 분석 시간만큼 HTTP 요청이 유지되고, 요청이 몰리면 일반 API까지 지연.
진단
장시간 분석이 HTTP 요청 내부에서 실행되며 일반 API와 같은 실행 환경을 공유. CPU 집약적인 처리와 추론이 요청 처리 자원을 점유해 분석 시간에 비례해 응답 시간이 증가.
해결
기존 · Client → FastAPI → 매출 분석 → 결과 반환
개선 · Client → FastAPI → Redis Queue → Celery Worker → 매출 분석
  1. FastAPI는 요청을 Redis Queue에 등록하고 Job ID를 즉시 반환
  2. CPU 사용량이 높은 작업은 Celery Worker가 전담, API 서버와 독립적으로 Worker 수 확장
  3. Job API로 상태 조회, 60초 주기로 queued 20분·running 15분 초과 작업을 FAILED 처리
결과
  • 동시 분석 요청 50건: p50 200.2s → 2.8s (98.6%↓), p95 221.4s → 4.3s (98.1%↓)
  • 요청 스레드 장시간 점유 해소, Worker 수 조절로 처리량 확장 구조 확보

Architecture

TroubleshootingRDB 검색 병목과 Elasticsearch 인덱스 정합성 문제
문제
AI 코스 생성 중 장소 후보를 PostgreSQL에서 반복 조회하면서 복합 조건 검색 부하가 증가, 검색 응답과 코스 생성 시간이 함께 지연.
진단
다양한 조건의 문자열 검색·다중 필터링이 RDB에 집중. Elasticsearch 도입 후에는 PostgreSQL 변경이 인덱스에 자동 반영되지 않는 정합성 문제도 발생.
해결
  1. 검색 구조 개선 — 검색 부하를 트랜잭션 DB에서 분리해 Elasticsearch 통합 인덱스와 복합 조건 검색 API로 전환
  2. CDC 파이프라인 — PostgreSQL을 원본으로 두고 Debezium이 변경을 Kafka로 발행, Spring Kafka Consumer가 인덱스 생성·수정·삭제
  3. 장애 복구 검증 — ES를 약 20초 중지하자 복구 후에도 미반영. 재시도(약 7초)가 장애보다 짧아 DLT로 넘어가 로그만 남은 것이 원인 → 지수 backoff로 약 61초까지 연장, DLT는 장소 ID만 기록하고 스케줄러가 DB 최신값으로 재색인해 순서 역전까지 방지
결과
  • 검색 API p95 99.3ms → 18.2ms (81.7%↓), p99 148.5ms → 26.6ms (82.1%↓), 처리량 19.8%↑
  • DB 변경 → 검색 반영 p95 1,054ms, 30회 반복 전건 반영
관측

Prometheus·Grafana — HTTP 처리량·p95·Kafka Consumer Lag 대시보드

배운 점
검색 성능은 쿼리 튜닝보다 트랜잭션과 검색을 분리하고 목적에 맞는 저장소를 고르는 문제이며, 동기화·재처리·모니터링까지 함께 설계해야 한다.

Architecture

Troubleshooting 1동기 HTTP 크롤링 Timeout과 요청 생명주기 결합
문제
Spring Boot와 Python 크롤러를 동기 HTTP로 연동. 약 41건 수집에 평균 20.4초가 걸렸지만 RestTemplate Read Timeout은 10초라 요청 실패.
진단
크롤러는 계속 실행 중인데 Spring Boot가 먼저 Timeout. 크롤링 시간이 늘면 같은 문제가 반복되는 구조.
해결
Timeout을 늘리는 대신 요청과 작업의 생명주기를 분리.
기존 · Request → Spring Boot → Python Crawler → 완료 대기 → Response
개선 · Request → Spring Boot → Kafka Producer → 202 Accepted
       Kafka → Consumer → Python Crawler → 내부 API → DB 저장
결과
  • 요청 접수 API 평균 3.5ms / p95 8ms, 크롤링 시간과 무관하게 Timeout 제거
배운 점
장시간 작업은 Timeout 값을 키우기보다 요청과 실행 흐름을 분리해야 하며, Kafka는 서비스 간 작업 생명주기를 분리하는 도구가 된다.
Troubleshooting 2반복 RDB 조회로 인한 추천 후보 조회 성능·DB 부하
문제
추천 점수 계산에 쓰는 카테고리별 최신 뉴스를 요청마다 MySQL에서 조회. 사용자별 결과는 달라도 후보 뉴스는 공통이라 같은 쿼리가 반복 실행.
진단
조회 빈도는 높고 변경 주기는 낮은 데이터를 매번 DB에서 읽어 불필요한 부하가 누적.
해결
기존 · Request → Spring Boot → MySQL → 추천 점수 계산 → Response
Hit  · Request → Redis 조회 → 추천 점수 계산 → Response
Miss · Request → MySQL 조회 → Redis 저장(TTL 10분) → 추천 점수 계산
Kafka Consumer가 크롤링 결과를 처리하며 MySQL과 Redis 후보 뉴스를 함께 갱신.
결과
  • 평균 조회 2.848ms → 2.238ms (21.4%↓)
  • 동시성 100 기준 p95 36.554ms → 11.670ms (68.1%↓)
배운 점
캐시 대상은 조회 빈도와 변경 주기로 골라야 하며, Cache-Aside는 응답 시간뿐 아니라 DB 부하 완화에도 효과적이다.
