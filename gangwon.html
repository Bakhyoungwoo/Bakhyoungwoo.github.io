Troubleshooting

트러블 슈팅

Trouble 01

RDB 기반 검색 병목과 Elasticsearch 인덱스 정합성 문제

문제

AI 여행 코스 생성 과정에서 관광지·음식점·숙소 후보를 PostgreSQL에서 반복 조회하면서 복합 조건 검색 부하가 증가했습니다. 이로 인해 장소 검색 응답이 지연되고, AI 여행 코스 생성 시간까지 길어졌습니다.

진단

지역·테마·반려동물 동반 여부·휠체어 접근성·편의시설·영업시간 등 다양한 조건이 조합되면서 문자열 검색과 다중 필터링이 RDB에 집중되었습니다. 또한 Elasticsearch 도입 이후 PostgreSQL의 변경 사항이 검색 인덱스에 자동 반영되지 않아 데이터 정합성 문제도 발생했습니다.

해결
01
검색 구조 개선 - 검색 부하를 트랜잭션 DB에서 분리하기 위해 Elasticsearch 기반으로 전환하고, 복합 조건을 지원하는 통합 검색 API 구현
02
CDC 파이프라인 구축 - PostgreSQL을 원본으로 유지하고 Debezium이 변경 사항을 Kafka로 전달, Spring Kafka Consumer가 인덱스를 생성·수정·삭제하고 일시적 실패는 Retry Topic으로 재처리
03
장애 복구 검증 및 개선 - ES를 약 20초 중지하고 DB를 수정하자 복구 후에도 미반영. 재시도 시간(약 7초)이 장애 시간보다 짧아 이벤트가 DLT로 이동했고, DLT가 로그만 남긴 것이 원인. 재시도를 지수 backoff로 약 61초까지 늘리고, DLT 이벤트는 장소 ID만 기록해 스케줄러가 PostgreSQL 최신값으로 재색인하도록 변경해 순서 역전도 방지

배운 점

검색 성능 문제는 쿼리 최적화만으로 해결하기보다 트랜잭션 처리와 검색 기능을 분리하고, 각 목적에 맞는 저장소를 선택해야 한다는 점을 배웠습니다. 또한 성능뿐 아니라 데이터 동기화, 장애 발생 시 재처리, 운영 모니터링까지 함께 설계해야 함을 경험했습니다.
