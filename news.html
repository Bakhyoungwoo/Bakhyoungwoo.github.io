01프로젝트 소개

실시간으로 수집한 뉴스와 금융 데이터를 AI로 분석해 사용자 맞춤형 뉴스와 종목 정보를 제공하는 AI 금융·뉴스 플랫폼입니다. 뉴스 크롤링, 키워드 추출, 사용자 관심사 및 클릭 이력 분석을 통해 개인화된 뉴스를 추천하고, 주식 시세·재무정보·관련 뉴스와 AI 기반 종목 분석 기능을 제공합니다. 또한 Redis, Kafka를 활용해 실시간 데이터 처리와 빠른 검색·추천 서비스를 구현했습니다.

사용자 기능

  • 관심 카테고리별 최신 뉴스 조회
  • 뉴스 클릭 이력 기반 개인 맞춤형 뉴스 추천
  • 카테고리별 주요 키워드 확인
  • 주요 시장 지수 및 종목 정보 조회
  • 종목 검색, 주가 차트·재무정보·관련 뉴스 확인
  • 기간별 주식 데이터 기반 AI 분석 결과 확인

04핵심 기여

Kafka 비동기 뉴스 수집

평균 20.4초 걸리는 크롤링이 10초 Read Timeout을 넘던 문제를 Producer/Consumer 구조로 해결. 요청은 즉시 202 Accepted.

Timeout 실패 제거 · 접수 API 평균 3.5ms / p95 8ms

Redis Cache-Aside 캐싱

여러 사용자가 공통으로 쓰는 카테고리별 추천 후보 뉴스를 캐싱, 10분 TTL로 최신성 유지. Consumer가 MySQL·Redis를 함께 갱신.

동시 100 · p95 36.6ms → 11.7ms (68.1%↓)

KR-SBERT 키워드 추출

Okt 형태소 분석과 불용어 필터링 후 KeyBERT·MMR로 키워드 추출, Redis ZSET으로 실시간 랭킹과 개인화 관심도 관리.

조사·어미 포함 86.7% → 0% · 처리 48.35s → 1.47s

장애 격리 · 모니터링

외부 AI(OpenBB) 장애 시 Fallback 응답으로 전파 차단, 한글 종목명 URL 이중 인코딩 버그 수정. Prometheus·Grafana로 Consumer Lag·응답시간 관측.

05트러블 슈팅
Troubleshooting 1동기 HTTP 크롤링 Timeout과 요청 생명주기 결합
문제
Spring Boot와 Python 크롤러를 동기 HTTP로 연동. 약 41건 수집에 평균 20.4초가 걸렸지만 RestTemplate Read Timeout은 10초라 요청 실패.
진단
크롤러는 계속 실행 중인데 Spring Boot가 먼저 Timeout. 크롤링 시간이 늘면 같은 문제가 반복되는 구조.
해결
Timeout을 늘리는 대신 요청과 작업의 생명주기를 분리.
기존 · Request → Spring Boot → Python Crawler → 완료 대기 → Response
개선 · Request → Spring Boot → Kafka Producer → 202 Accepted
       Kafka → Consumer → Python Crawler → 내부 API → DB 저장
결과
  • 요청 접수 API 평균 3.5ms / p95 8ms, 크롤링 시간과 무관하게 Timeout 제거
배운 점
장시간 작업은 Timeout 값을 키우기보다 요청과 실행 흐름을 분리해야 하며, Kafka는 서비스 간 작업 생명주기를 분리하는 도구가 된다.
Troubleshooting 2반복 RDB 조회로 인한 추천 후보 조회 성능·DB 부하
문제
추천 점수 계산에 쓰는 카테고리별 최신 뉴스를 요청마다 MySQL에서 조회. 사용자별 결과는 달라도 후보 뉴스는 공통이라 같은 쿼리가 반복 실행.
진단
조회 빈도는 높고 변경 주기는 낮은 데이터를 매번 DB에서 읽어 불필요한 부하가 누적.
해결
기존 · Request → Spring Boot → MySQL → 추천 점수 계산 → Response
Hit  · Request → Redis 조회 → 추천 점수 계산 → Response
Miss · Request → MySQL 조회 → Redis 저장(TTL 10분) → 추천 점수 계산
Kafka Consumer가 크롤링 결과를 처리하며 MySQL과 Redis 후보 뉴스를 함께 갱신.
결과
  • 평균 조회 2.848ms → 2.238ms (21.4%↓)
  • 동시성 100 기준 p95 36.554ms → 11.670ms (68.1%↓)
배운 점
캐시 대상은 조회 빈도와 변경 주기로 골라야 하며, Cache-Aside는 응답 시간뿐 아니라 DB 부하 완화에도 효과적이다.
