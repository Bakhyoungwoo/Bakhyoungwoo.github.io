주제

뉴스 크롤링, 키워드 추출, 사용자 관심사 및 클릭 이력 분석을 통해 개인화된 뉴스를 추천하고, 주식 시세·재무정보·관련 뉴스와 AI 기반 종목 분석 기능을 제공합니다. 또한 Redis, Kafka를 활용해 실시간 데이터 처리와 빠른 검색·추천 서비스를 구현했습니다.

주요 기능

사용자 기능

  • 관심 카테고리별 최신 뉴스 조회
  • 뉴스 클릭 이력 기반 개인 맞춤형 뉴스 추천
  • 카테고리별 주요 키워드 확인
  • 주요 시장 지수 및 종목 정보 조회
  • 종목 검색, 주가 차트·재무정보·관련 뉴스 확인
  • 기간별 주식 데이터 기반 AI 분석 결과 확인

전체 아키텍처

Spring Boot가 API와 비즈니스 로직을, FastAPI가 크롤링과 AI 분석을 담당하며 두 서버는 Kafka로 연결됩니다. MySQL에 뉴스와 사용자 데이터를 저장하고, Redis로 추천 후보 캐싱과 키워드 랭킹을 관리합니다. 전체 서비스는 Docker로 구성하고 GitHub·Docker Hub 기반으로 배포합니다.

Redis Cache-Aside 기반 뉴스 조회 캐싱

여러 사용자가 공통으로 조회하는 카테고리별 추천 후보 뉴스를 요청마다 MySQL에서 반복 조회해 불필요한 DB 부하가 쌓이는 구조였습니다. Redis에 우선 캐싱하고 캐시 미스 시에만 MySQL을 조회해 채우는 Cache-Aside 패턴을 적용하고, 오래된 데이터 방지를 위해 10분 TTL을 설정했습니다.

Troubleshooting

트러블 슈팅

Trouble 01

동기 HTTP 크롤링 Timeout 및 요청 생명주기 결합

문제

Spring Boot와 Python 크롤러를 동기 HTTP로 연동한 이후, 크롤링 작업이 HTTP Timeout을 초과해 요청이 실패했습니다. 약 41건의 뉴스를 수집하는 데 평균 20.4초가 걸렸지만 RestTemplate의 Read Timeout은 10초로 설정되어 있었습니다.

진단

크롤링이 완료될 때까지 Spring Boot가 HTTP 응답을 대기하는 구조였습니다. Python 크롤러는 계속 실행 중이었지만 Spring Boot에서 먼저 Timeout이 발생했고, 크롤링 시간이 늘어나면 같은 문제가 반복될 수 있었습니다.

해결
기존 · Request → Spring Boot → Python Crawler → 완료 대기 → Response
개선 · Request → Spring Boot → Kafka Producer → 202 Accepted
Kafka → Consumer → Python Crawler → Spring 내부 API → DB 저장
01
생명주기 분리 - Timeout을 늘리는 대신 크롤링 작업과 API 요청의 생명주기를 Kafka로 분리
02
즉시 응답 - 메시지 발행에 성공하면 202 Accepted를 즉시 반환
03
비동기 저장 - Consumer가 크롤러를 호출하고, 결과는 Spring 내부 API로 DB에 저장
결과

배운 점

장시간 작업에서는 Timeout 값을 늘리는 것보다 API 요청과 실제 작업의 실행 흐름을 분리하는 것이 중요하다는 점을 배웠습니다. Kafka는 단순한 메시지 전달을 넘어 서비스 간 작업 생명주기를 분리하는 도구가 될 수 있음을 경험했습니다.

Trouble 02

반복적인 RDB 조회로 인한 추천 후보 조회 성능 및 DB 부하

문제

사용자 관심사 기반 뉴스 추천에서 추천 후보로 쓰이는 카테고리별 최신 뉴스 목록을 요청마다 MySQL에서 조회했습니다. 추천 결과는 사용자마다 달라도 후보 뉴스는 공통 데이터라, 요청이 늘수록 같은 쿼리가 반복 실행되었습니다.

진단

추천 후보 뉴스는 조회 빈도가 높고 변경 주기가 상대적으로 낮은데도 매 요청마다 MySQL을 직접 조회하고 있었고, 이로 인해 불필요한 DB 접근과 부하가 누적될 수 있다고 판단했습니다.

해결
기존 · Request → Spring Boot → MySQL → 추천 점수 계산 → Response
개선 · Request → Spring Boot → Redis 조회
Cache Hit → 추천 점수 계산 → Response
Cache Miss → MySQL 조회 → Redis 저장 → 추천 점수 계산 → Response
01
Cache-Aside 적용 - API 요청 시 Redis를 먼저 조회하고, 캐시가 없거나 만료된 경우에만 MySQL 조회 후 Redis에 저장
02
캐시 갱신 연동 - 1번 트러블 슈팅의 Kafka Consumer가 크롤링 결과를 처리하면서 MySQL과 Redis의 추천 후보를 함께 갱신
결과
21.4%↓
평균 조회 시간
2.848ms → 2.238ms
68.1%↓
동시성 100 p95

배운 점

캐시는 모든 데이터를 저장하는 것이 아니라 조회 빈도와 데이터 변경 주기를 고려해 대상을 선정해야 한다는 점을 배웠습니다. Cache-Aside 패턴은 응답 시간 개선뿐 아니라 반복적인 RDB 접근을 줄여 DB 부하를 완화하는 데 효과적이었습니다.
